1. COLLABORATION, POOLS, AND LANES (POOL & SWIMLANE DIVISION):
   - MANDATORY COLLABORATION RULE: Every diagram with Pools or Lanes MUST define a <bpmn:collaboration> element containing one or more <bpmn:participant> (Pools) that reference their respective processes (e.g., processRef="Process_ID").

2. SPECIFIC TASK TYPES & NAMING CONVENTIONS:

     * User Task (<bpmn:userTask>) for activities done by a human through an interface (e.g., "Nhập thông tin", "Duyệt yêu cầu").
     * Service Task (<bpmn:serviceTask>) for automatic system operations (e.g., "Gửi email thông báo", "Lưu cơ sở dữ liệu").
     * Manual Task (<bpmn:manualTask>) for physical human actions without software (e.g., "Giao hàng").
     * Script Task (<bpmn:scriptTask>) or Business Rule Task where appropriate.
   - TASK NAMING CONVENTION: Task names MUST follow the pattern: [Động từ hành động] + [Đối tượng xử lý] + [Bối cảnh/Hệ thống nếu cần]. Examples:
     * Good: "Admin tạo đơn Enterprise trên Admin Console", "Hệ thống lưu thông tin vào DB License", "Kế toán đối soát & duyệt PAID trên hệ thống"
     * Bad: "Xử lý", "Thao tác", "Bước tiếp theo" (too vague, missing object and context)

3. GATEWAYS, VALIDATION PROCESSES, AND ACTION TRIGGERS:
   - Exclusive Gateway (<bpmn:exclusiveGateway>) for decision/branching points where only one path is taken. Name the gateway with a question (e.g., "Duyệt thành công?"), and label outgoing flows with answers (e.g., name="Yes", name="No"). Each outgoing flow must have a valid <bpmn:conditionExpression>.
   - Gateway Outgoing Flow Labels: Do not limit labels to just simple "Yes" or "No". Use descriptive business outcomes or check results directly on the sequence flows (e.g., name="Vi phạm", name="Pass", name="Thành công", name="Thất bại", name="Có nhu cầu gia hạn", name="Không có nhu cầu", name="PERSONAL", name="ENTERPRISE").
   - Parallel Gateway (<bpmn:parallelGateway>) for paths running concurrently. Every divergent parallel gateway must have a corresponding convergent parallel gateway (Join) to synchronize the flows before moving forward.
   - Parallel Gateway vs Multi-Type Classifier: When a process splits into multiple parallel configuration flows or independent resource types (e.g., configuring Storage, OCR, Token, and License in parallel), use a Parallel Gateway (<bpmn:parallelGateway>) with a plus (+) symbol.
   - Inclusive Gateway (<bpmn:inclusiveGateway>) where multiple conditions can be true.
   - Ensure proper convergence: merge branches back before reaching an End Event.
   - NO MULTIPLE INCOMING FLOWS ON TASKS/EVENTS (ANTI-FAKE-JOIN RULE): Never connect multiple incoming sequence flows directly to a single Task or End Event. If multiple paths converge, you MUST merge them first using an explicit Join Gateway (Exclusive Gateway <bpmn:exclusiveGateway> if paths are exclusive/conditional, or Parallel Gateway <bpmn:parallelGateway> if paths are concurrent/parallel) before connecting to the target Task/Event. This avoids "fake-join" validation errors.
   - LOOP-BACK AND START MERGE RULE (CRITICAL): If a User Task (e.g., "Nhập thông tin") is the target of a validation loop-back (retry flow) and is also preceded by a Start Event, you MUST NOT connect both the Start Event and the loop-back flow directly to the User Task. Instead, insert an Exclusive Gateway (<bpmn:exclusiveGateway> serving as a merge point) immediately BEFORE the User Task. Connect both the Start Event and the loop-back flow to this Merge Gateway, and then connect the Merge Gateway to the User Task via a single sequence flow.
   - CONDITIONAL UI BEHAVIOR (DYNAMIC FORM LOGIC): When a dropdown, radio button, or toggle changes value and triggers different UI states (e.g., fields being locked, hidden, or dynamically populated), you MUST model this as:
     * An Exclusive Gateway immediately after the selection task, with outgoing flows labeled by the selected option (e.g., "PERSONAL", "ENTERPRISE").
     * Each branch leads to a Service Task or annotation describing the specific UI behavior change (e.g., "Hệ thống khóa field: chỉ cho chọn 1 License, default_quantity = 1" vs "Cho phép chọn nhiều License, nhập default_quantity tùy ý").
     * Attach a Text Annotation to the Gateway or branch task detailing exactly which fields are locked/unlocked/hidden/shown.
   - VALIDATION TIMING & ACTION TRIGGERS (CRITICAL): When process validation is required (e.g., checking for duplicate names, format checking), you must visually model the exact trigger action and timing:

     * Click-to-Validate Action: If checking only happens when the user clicks a button (e.g., clicking "Lưu/Tạo"), you MUST represent this as an explicit sequence flow or intermediate event indicating the action and the actor (e.g., flow name: "Nhấn nút Lưu (Admin)").
     * Validation Fail Path & Errors: If the validation fails, the flow MUST loop back to the input User Task. The loop-back sequence flow MUST be labeled with the specific error message or UI visual cues shown to the user (e.g., flow name: "Trùng tên (Báo lỗi đỏ trên UI)", or "Thiếu trường bắt buộc (Hiển thị dấu * đỏ)").
